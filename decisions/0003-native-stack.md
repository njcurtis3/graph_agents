# ADR 0003 — Native stack: Expo for mobile, Tauri 2 for desktop, builds in the cloud

**Date:** 2026-10-07
**Status:** Accepted
**Scope:** `graph_agents/` only. An app is free to decide differently inside its own repo.

## The decision

When an app ships as a native binary, the fleet builds it with:

- **Mobile (iOS + Android): Expo** (React Native, TypeScript) with **Continuous Native
  Generation**, built and submitted with **EAS** (Build, Submit, Update).
- **Desktop (Windows, macOS, Linux): Tauri 2** (Rust core, system webview, web frontend).
- **iOS builds run on EAS cloud.** macOS Tauri builds, signing and notarization run on a
  **GitHub Actions macOS runner** in the `TelosRG` org; Linux builds on an ubuntu runner;
  Windows builds locally or on a windows runner.

The two conventions that enforce it are `conventions/native-mobile.md` and
`conventions/native-desktop.md`. The routing predicate is the registry's `ui` field.

## Context

**The owner develops on Windows and has no Mac.** That fixes more than it seems to. Xcode
only runs on macOS, so no iOS binary, and no signed and notarized macOS binary, can be made
on this machine. Both must come from a build someone else's Mac produces: EAS for iOS, a
hosted macOS runner for Tauri on macOS. The stack is chosen so that nothing ever requires
opening Xcode by hand.

**Why Expo over bare React Native.** A bare RN project commits `ios/` and `android/`, and
those directories need Xcode and Android Studio to maintain. With Continuous Native
Generation, `ios/` and `android/` are **generated by `expo prebuild` and not committed**.
Native configuration lives in `app.config.ts` (or `app.json`) and in **config plugins**;
EAS Build runs prebuild in the cloud. Nobody here can maintain an Xcode project, so the
stack removes the need to.

**Why Expo over Tauri mobile.** Tauri 2 supports iOS and Android, but its mobile path
still needs Xcode and the Android SDK locally for development, has a much smaller plugin
and library ecosystem than React Native, and has no equivalent of EAS Update. Expo has a
managed cloud build, OTA updates, and a mature module set (`expo-router`,
`expo-secure-store`, `expo-notifications`). Tauri stays the desktop choice, where its
small binaries and Rust core are the strength.

**Why Tauri over Electron for desktop.** Small installers, a deny-by-default permission
model (capabilities), and a Rust backend. The cost is that the webview is the OS's:
WebView2 on Windows, WKWebView on macOS, WebKitGTK on Linux, so rendering and API support
differ per OS. The desktop convention treats that as a rule to test against, not a
surprise.

**The cost of the cloud.** EAS has free-tier build limits and queue times, and Apple
requires a paid developer account for TestFlight and the App Store. Signing credentials are
managed by EAS; macOS signing secrets live in the GitHub org's Actions secrets.

## What would reverse this

- **The owner gets a Mac.** Local iOS builds and local macOS signing become possible, and
  the runner and EAS dependency shrink to a convenience. It would not by itself reverse
  Expo or Tauri.
- **EAS limits or pricing** stop fitting the build volume, or queue times block iteration.
  The fallback is local or self-hosted builds of the same prebuild output.
- **A native capability Expo cannot reach** even through a custom config plugin or
  development build. Then that app drops to a bare workflow, which reopens the Xcode problem.
- **A Tauri webview gap on a target OS** that a required feature cannot live with (for
  instance an API missing in WebKitGTK that the app depends on). Then that app considers
  Electron, which bundles Chromium.
- **Tauri mobile matures**: a stable plugin ecosystem, no required local Xcode, and an
  update story. Then one codebase for desktop and mobile becomes worth re-weighing.

## This is a decision record, not a dependency

Nothing reads this file at runtime. Delete it and no build, hook or agent breaks; only the
next reader's ability to skip the argument goes with it.
