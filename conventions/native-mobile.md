# Convention — native mobile (Expo, built on EAS)

An app that ships to a phone's app store is judged by the phone's rules, not the web's.
This file is the bar for Expo apps. It is prose and checklists, nothing more — see § This
is a convention, not a dependency at the bottom before you wire anything to this path. The
stack choice itself is `decisions/0003-native-stack.md`.

## Does this apply?

**It applies when the app's `ui` in `graph_agents/portfolio/registry.json` includes
`native-mobile`.** `ui` may be a single string or an array; an app with
`["responsive-web", "native-mobile"]` is bound by this file for its native target and by
`mobile-first.md` for its web target.

It does not apply to `responsive-web` alone, `desktop-only` or `none`. Desktop binaries
are `native-desktop.md`.

## Stack and project shape

- **Expo with Continuous Native Generation.** `ios/` and `android/` are generated by
  `expo prebuild` and **not committed** (they are in `.gitignore`). Native configuration is
  `app.config.ts` (or `app.json`) plus config plugins. Nobody here can maintain an Xcode
  project.
- **Navigation: `expo-router`.** File-based routes; platform conventions (stack, tabs,
  modal) are used as the platform uses them.
- **iOS builds happen on EAS.** There is no Mac; never write a step that needs Xcode locally.
- **`eas.json` defines three build profiles**: `development` (development client,
  internal distribution), `preview` (internal distribution, store-like), `production` (store
  distribution, `autoIncrement` for build numbers). Each has a `channel` for EAS Update.

## Layout and input

- **Safe areas.** Use `react-native-safe-area-context` (`SafeAreaProvider`, `useSafeAreaInsets`
  or `SafeAreaView`) so content clears the notch, Dynamic Island, home indicator and Android
  system bars. No hard-coded status-bar or notch heights.
- **Touch targets: >= 44pt on iOS, >= 48dp on Android.** An icon smaller than that gets
  padding or `hitSlop` to reach it. Keep >= 8pt (iOS) / 8dp (Android) between adjacent targets.
- **Android back.** The hardware/gesture back button must do the platform thing: pop the
  stack, close a modal, then exit. With `expo-router` this is the default; a custom
  `BackHandler` must return `true` only when it handled the event.
- **Keyboard.** Forms use `KeyboardAvoidingView` (or equivalent) so the focused field stays
  visible; inputs set `keyboardType`, `autoComplete` and `textContentType`.

## Network and offline

- Assume the network is absent. Every screen that loads remote data has a loading, an
  error and an offline state, not just a success state.
- Read connectivity from `expo-network` (or `@react-native-community/netinfo`), never infer
  it from a failed fetch alone.
- Writes made offline are queued or visibly refused; they are never silently dropped.

## Permissions

- **Rationale before the prompt.** Explain in the app why a permission is needed, then call
  the request. The OS prompt is shown once on iOS; spending it cold wastes it.
- **A denied path.** Denial is a normal state: the feature degrades, and where the OS will
  not re-prompt, the UI offers `Linking.openSettings()`.
- **Usage strings live in `app.config`.** iOS `infoPlist` `NS*UsageDescription` keys (or the
  module's config plugin options) and the Android `permissions` list are declared there, not
  in a generated `Info.plist` or `AndroidManifest.xml`. Request only what a shipped feature uses.

## Secrets and storage

- **Secrets, tokens and credentials go in `expo-secure-store`** (Keychain / Keystore).
- **`AsyncStorage` is for non-sensitive state only** — preferences, caches, drafts. It is
  unencrypted. Never put a token, password or key in it.
- **No secret in the bundle.** `EXPO_PUBLIC_*` variables are inlined into the JavaScript
  that ships; anything there is public. Real secrets stay server-side, or live in EAS
  environment variables with `secret` or `sensitive` visibility (not the deprecated
  `eas secret:*` commands), used at build time for build tooling only.

## Updates and runtime versions

- **`runtimeVersion` is set explicitly** in `app.config`. **The default policy is
  `fingerprint`** (a hash of the native layer), so any native change yields a new runtime
  version by itself and old binaries never receive an incompatible update. Never leave it
  unset when `expo-updates` is installed.
- **`appVersion` is allowed only with the bump rule.** Under `appVersion`, every native
  change (a new native module, a config plugin change, an SDK bump, a native field in
  `app.config`) **MUST bump `version`** in the same change, before the next `eas update`.
  `autoIncrement` in `eas.json` raises only `buildNumber` / `versionCode`, not `version`, so
  it does not satisfy this rule. Without the bump, the update reaches old binaries that lack
  the native code.
- **OTA updates carry JavaScript and assets only.** Anything that changes native code —
  a new native module, a config plugin change, a permission, an SDK upgrade — needs a **new
  build**.
- **Updates are published to a channel** (`eas update --channel <name>`) matching the build
  profile, never straight to `production` without passing `preview`.
- Store submission goes through `eas submit`; credentials are managed by EAS.

## Accessibility

- Every interactive element has `accessibilityLabel` and `accessibilityRole` (or the
  `aria-*` equivalents React Native now supports); state is exposed via `accessibilityState`.
- **Font scaling is respected** (Dynamic Type on iOS, font scale on Android). No
  `allowFontScaling={false}` on body text, and layouts survive 200% text without clipping.
- Decorative images are hidden from the screen reader; informative ones have a label.

## Prohibitions — each one visible in a diff

(Except the OTA rule, which is visible in a diff only when `eas update` runs from a
committed CI workflow; a manual `eas update` leaves no diff and is an ops-gate rule.)

- **No committed `ios/` or `android/` directory** in a Continuous Native Generation app.
- **No token, password or API secret in `AsyncStorage`**, and none in an `EXPO_PUBLIC_*` variable.
- **No hard-coded safe-area, status-bar or notch heights.**
- **No interactive element under 44pt / 48dp** without `hitSlop` or padding that reaches it.
- **No native module, config-plugin or permission change shipped as an OTA update.**
  Enforce in the CI workflow that publishes; a manual `eas update` is covered by the
  ops-gate, not a diff.
- **No native change under `appVersion` without a `version` bump**, and no unset
  `runtimeVersion` alongside `expo-updates`.
- **No `allowFontScaling={false}`** on body text.
- **No permission request without a rationale and a denied path**, and no usage string
  edited anywhere but `app.config`.
- **No step in a script or CI that requires Xcode or a Mac** outside EAS.

## Reviewer checklist

Yes/no, answerable by reading a diff. `reviewer.md` points here by name.

1. Is `ios/` and `android/` absent from the diff, and ignored in `.gitignore`?
2. Are secrets and tokens stored only via `expo-secure-store`, with `AsyncStorage` used for
   non-sensitive values and no secret in `EXPO_PUBLIC_*`?
3. Do new screens use `react-native-safe-area-context` insets rather than fixed offsets?
4. Does every new interactive element reach >= 44pt / 48dp by size, padding or `hitSlop`?
5. Does a new remote-data screen have loading, error and offline states?
6. Does every new permission have a rationale before the request, a denied path, and its
   usage string / permission entry in `app.config`?
7. If native code, plugins, permissions or native dependencies (`package.json`) changed, is
   it shipped as a new build (not an `eas update`), and is `runtimeVersion` policy
   `fingerprint`, or under `appVersion` does the same diff bump `version`?
8. Does `eas.json` keep `development`, `preview` and `production` profiles with channels?
9. Do new interactive elements have `accessibilityLabel` and `accessibilityRole`, with font
   scaling left on?
10. Does a custom Android back handler return `true` only when it handled the event?

Anything you cannot answer from the diff (real-device behavior, store review) is a
**note**, not a rejection.

## This is a convention, not a dependency

This file is **read and copied as guidance**. No app may import it, build against it, or
resolve this path at build, test or deploy time. An app's `CLAUDE.md` may *name* this path
for a human reader. The mechanical test: delete `graph_agents/` from disk, and every app
must still clone, install, test and build.

When a new app is born with `native-mobile` in its `ui`, the rules above get **copied into
that app's own `CLAUDE.md`** under `## Native targets`, then owned locally and allowed to
drift. Copy, don't couple.

See `graph_agents/CLAUDE.md` § The one invariant.
